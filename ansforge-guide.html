⚙️ ansible — guide interne des pratiques

Un agent IA qui valide de l'Ansible en l'exécutant — parce que le lint ne voit que la forme

Ta fiche de référence : ce que fait chaque partie de l'agent, pourquoi ça compte, et ce que tu peux en dire en entretien. Le pari ici : un playbook vert au lint peut être faux à l'exécution — et c'est démontrable.

5 pratiques · éprouvées sur une plateforme AWS réelle · 3 bugs documentés · lecture ~12 min

En une phrase : la méthode pour qu'un agent IA écrive de l'Ansible sans casser une flotte — rendre les templates par Ansible lui-même (pas par un script Python qui fournit les variables à la main), valide le résultat avec l'outil amont (nginx -t, promtool, logrotate) dans l'image épinglée, puis lance le conteneur et appelle l'endpoint réel. Le différenciateur, ce n'est pas « un LLM qui écrit du YAML » — c'est la preuve d'exécution, et le fait que l'agent ne peut pas toucher une machine réelle.

Trois bugs d'un projet réel sont passés à travers ansible-lint en profil production. Aucun n'était détectable sans exécuter. C'est ce constat qui définit l'outil : le lint valide la forme, l'exécution valide le comportement.

🧪

Prouver pas promettre

Un contrôle qui ne peut pas échouer ne prouve rien. L'agent casse volontairement l'entrée, vérifie que le contrôle sort en erreur, puis restaure.

🔒

Lecture seule sur l'infra

L'agent rend, exécute en conteneur jetable, rapporte. Il n'a aucun accès aux instances : appliquer reste une décision humaine.

🔁

Idempotence vérifiée

Un playbook se joue deux fois : le second passage doit être changed=0. Sinon il n'est pas idempotent, quoi qu'en dise le lint.

Rendre pour de vrai (le déclic)

2 outils

La majorité des bugs Ansible tiennent à une variable qui n'existe pas dans le contexte réel. Un script de test qui fournit les variables à la main ne les verra jamais.

render_template — rendu par Ansible, pas par Jinja2 nu
C'est quoi
L'outil rend chaque .j2 via ansible localhost -m ansible.builtin.template, chargé avec les vrais group_vars et les defaults des rôles — exactement le mécanisme de production.
Le problème
Un test en Jinja2 pur passe alors que le run réel échoue. Cas vécu : {{ ansible_managed }} placé dans un content: du module copy. Cette variable n'est injectée que par le module template. Le lint validait la syntaxe, le test Python fournissait la variable à la main, et l'instance a planté au premier boot.
Pourquoi ça compte
C'est la différence entre « la syntaxe est valide » et « ça produira le bon fichier sur la machine ». Seul le second est une garantie.
validate_rendered — l'outil amont, dans l'image épinglée
C'est quoi
Le fichier rendu part dans le binaire qui le consommera : nginx -t, promtool check config, amtool check-config, docker compose config, logrotate -f.
Dans l'image épinglée
Pas avec le binaire du poste. Une directive acceptée par nginx 1.27 peut être refusée par une autre version — valider ailleurs que dans l'image de production ne prouve rien.
Fiabilité
Chaque validateur est réversible : l'agent injecte une faute, confirme le code de sortie non nul, restaure. Un contrôle non testé est un faux sentiment de sécurité.
À dire en entretien : « Je ne valide jamais un template Jinja avec un script Python : je le rends par Ansible, avec les vraies variables. Un bug de mon projet est passé à travers ansible-lint parce que la variable spéciale n'existe que dans le module template — le lint voyait du Jinja valide, la machine voyait une variable indéfinie. »

Exécuter (la killer feature)

conteneurs jetables

Rendre et valider ne suffit pas : il reste les erreurs de comportement, celles qu'aucun analyseur statique ne peut voir.

run_and_probe — lance, puis appelle l'URL du vrai consommateur
C'est quoi
Le conteneur est démarré avec la config rendue, puis l'agent appelle l'URL exacte que le consommateur appellera en production, depuis le bon endroit.
Le cas d'école
Une config nginx déclarait listen 127.0.0.1:8080 pour stub_status. nginx -t : valide. Mais dans un conteneur, cette adresse est la loopback du conteneur — inatteignable depuis l'hôte, où tourne l'exporter Prometheus. La supervision nginx serait tombée silencieusement.
Ce qu'on en tire
L'agent teste depuis l'hôte, pas depuis le conteneur. La nuance — mapping Docker contre loopback interne — est invisible à la lecture et évidente à l'exécution.
check_side_effects — ce que le changement a fait disparaître
Le problème
Un changement d'architecture retire des choses que personne n'avait listées. Conteneuriser nginx supprime le paquet RPM — donc /etc/logrotate.d/nginx qu'il fournissait. Plus aucune rotation : l'access log grossit jusqu'à saturer le volume racine.
La méthode
Pour chaque paquet ou service retiré, l'agent liste ce qu'il apportait (unités systemd, configs logrotate, utilisateurs, répertoires) et signale ce qui n'a pas de remplaçant. Aucun linter ne raisonne sur une absence.
Vérifié en conditions réelles
Le correctif logrotate a été testé dans un conteneur Linux : rotation jouée, et inode préservé — parce qu'un collecteur de logs qui suit le fichier perdrait sa position sinon. copytruncate n'est pas un détail cosmétique.
À dire en entretien : « Mon critère de succès n'est pas “le playbook est vert”, c'est “l'endpoint répond 200 et l'exporter arrive à scraper”. J'ai eu un cas où la config était syntaxiquement parfaite et fonctionnellement morte : un loopback de conteneur n'est pas celui de l'hôte. »

Sécurité — ce que l'agent ne peut pas faire

par construction

Un agent qui écrit de la configuration système est un vecteur. La réponse n'est pas la confiance, c'est le périmètre.

Moindre privilège, appliqué à l'agent
Pas d'accès aux machines
L'agent rend et exécute en conteneur local. Il n'a ni credentials cloud, ni accès SSM, ni inventaire de production. Converger une flotte reste une commande humaine.
Pas d'écriture sur le dépôt
Le rôle de relecture a des outils de lecture seule : il rapporte par fichier et ligne, l'humain applique. C'est le même raisonnement qu'un rôle IAM restreint à une action sur un seul préfixe.
Pas de secrets
Les tests tournent sur des variables d'exemple. Un mot de passe réel ne doit jamais entrer dans le contexte d'un modèle — et en contexte réglementé (santé, données personnelles), ça exclut aussi les extraits de logs applicatifs.
audit_playbook — les failles propres à Ansible
Ce qu'il cherche
Secrets en clair dans les vars, no_log absent sur une tâche qui manipule un mot de passe, shell avec interpolation non échappée, validate_certs: no, téléchargement sans checksum, become plus large que nécessaire.
Le motif qui revient
Un binaire téléchargé depuis une release GitHub sans somme de contrôle épinglée : c'est une exécution de code arbitraire à la première compromission du dépôt amont. Version et checksum se bumpent ensemble, jamais l'un sans l'autre.
Honnêteté
Ces heuristiques complètent ansible-lint, elles ne le remplacent pas. Un filet solide, pas une barrière absolue.
À dire en entretien : « L'agent n'a aucun accès aux machines ni aux secrets. Il rend, il exécute en conteneur jetable, il rapporte. La convergence reste une action humaine — un agent qui peut appliquer en production est un incident qui attend son heure. »

Dérive & idempotence

le contrat Ansible

L'idempotence est la promesse fondatrice d'Ansible, et la moins vérifiée. Un playbook qui rapporte changed à chaque passage rend la correction de dérive illisible.

idempotence_check — le second passage doit être vide
La méthode
Deux exécutions consécutives. La seconde doit rendre changed=0. Toute tâche encore changed est listée avec sa cause probable : command sans creates, copy d'un contenu daté, changed_when manquant.
Pourquoi ça compte
Quand un playbook est rejoué toutes les 30 minutes par un mécanisme de convergence, un faux changed noie les vrais. On finit par ne plus lire les rapports — et c'est là qu'une dérive réelle passe inaperçue.
Ordre d'exécution
L'agent signale les dépendances cachées : une section roles s'exécute avant les tasks. Un rôle qui suppose un répertoire créé plus tard dans le play échoue au premier boot d'une machine neuve — et uniquement là.
migration_path — l'existant n'est pas vierge
Le constat
Les tests se font sur une machine neuve ; la réalité, c'est une machine qui porte l'état laissé par la version précédente.
Cas vécu
Après conteneurisation, les instances existantes gardaient l'ancien service hôte qui détenait les ports 80 et 8080. Le conteneur ne pouvait pas démarrer. Le playbook doit arrêter explicitement l'ancien service — sans effet sur les machines neuves, qui ne l'ont jamais installé.
La règle
Tout changement qui remplace un composant doit décrire le chemin depuis l'ancien état. Un playbook qui ne fonctionne que sur une machine neuve n'est pas idempotent, il est amnésique.
À dire en entretien : « Je teste l'idempotence en jouant deux fois : le second passage doit être à zéro changement. Et je teste le chemin de migration, pas seulement l'installation — une instance existante porte l'état de la version précédente, c'est là que ça casse. »

Mode CI

non bloquant

L'agent produit un avis, pas un verdict. Un gate de CI doit rendre le même résultat sur le même diff — un modèle ne le garantit pas.

L'agent en CI — commentaire de PR, jamais d'échec
Ce qui bloque
Les contrôles déterministes, et eux seuls : ansible-lint, --syntax-check, les validateurs amont sur la config rendue. Reproductibles, donc opposables.
Ce qui ne bloque pas
L'analyse de l'agent : effets de bord, ordre d'exécution, chemin de migration, commentaires devenus faux. Utile à lire, jamais opposable. Un pipeline qui échoue de façon non reproductible détruit la confiance qu'on a en lui.
Coût
Analyse restreinte au diff, pas au dépôt entier. Le rapport indique les tokens consommés et leur coût : une dépense d'infrastructure se mesure.
À dire en entretien : « L'IA commente, elle ne bloque pas. Un gate de CI doit être déterministe : même diff, même verdict, sinon l'équipe apprend à le contourner. Les linters bloquent, l'agent conseille. »
