La boucle agentique (le déclic)

from scratch

Le cœur, et la raison d'être pédagogique du projet : comprendre comment un agent (comme Claude Code) marche vraiment, en le codant soi-même, sans framework.

La boucle : message → tool_use → garde → run → result → loop
C'est quoi
~100 lignes de Go : on envoie à l'API un message + la liste des outils ; le modèle répond soit du texte, soit « je veux appeler cet outil » ; on passe l'action par la garde, on l'exécute, on renvoie le résultat, et on boucle jusqu'à ce que le modèle ait fini.
Pourquoi from-scratch
Beaucoup « apprennent l'agentic » sans jamais voir la boucle. En la codant en HTTP brut sur l'API Anthropic (pas de LangChain/SDK), Claude Code cesse d'être magique — tu vois exactement le mécanisme. C'est le déclic.
Fiabilité
La boucle est bornée (30 tours max) pour qu'un modèle qui déraille ne tourne pas à l'infini. Le client du modèle est une interface → toute la boucle est testée avec un faux client, sans clé API ni tokens.
À dire en entretien : « J'ai écrit la boucle agentique moi-même sur l'API brute — je ne me contente pas d'utiliser un agent, je sais comment il est construit : le cycle tool_use, la gestion de l'historique de messages, le bornage anti-boucle. »

Construire & sécuriser (le « truc de fou »)

4 outils

L'agent ne fait pas qu'analyser : il écrit de l'infra, la scanne, et s'auto-corrige. C'est la boucle GÉNÈRE → VALIDE → SÉCURISE → AUTO-CORRIGE.

write_file — l'agent génère & réécrit le code build
C'est quoi
L'outil qui laisse l'agent écrire des fichiers .tf lui-même. C'est ce qui permet la génération ET l'auto-correction : il écrit le code, le scanne, puis réécrit une version corrigée.
Sécurité par défaut
Le system prompt impose des défauts sûrs quand l'agent génère : S3 privé + public-access block + chiffrement, IAM least-privilege (jamais Action "*"), chiffrement au repos, aucun secret en clair.
Confinement
Les chemins sont confinés sous la racine du projet et limités aux fichiers de config/texte — l'agent ne peut pas écrire hors du projet ni s'échapper via ...
security_scan — checkov + trivy/tfsec + analyse provider-aware
C'est quoi
Un scan de sécurité statique tolérant à l'outil disponible : il utilise checkov (référence Terraform), sinon trivy, sinon tfsec — ce qui est installé. Plus une passe maison qui signale les classiques en clair.
Ce qu'elle détecte
IAM avec Action/Resource en "*" (permissions trop larges), bucket S3 public, chiffrement S3/RDS/EBS absent, public-access-block manquant, secrets en clair dans le .tf — sans jamais afficher la valeur du secret.
L'auto-correction
Si le scan trouve des problèmes, l'agent réécrit le code pour les corriger et re-scanne — jusqu'à ce que ce soit propre. C'est la boucle qui rend l'agent vivant.
À dire en entretien : « Mon agent ne réimplémente pas checkov — il l'orchestre, et ajoute une analyse IAM provider-aware par-dessus. Surtout, il s'auto-corrige : il scanne, réécrit, re-scanne. En vrai, il a généré un stack S3 sécurisé que checkov a validé (13 checks passés, 0 échec). » — Honnête : les heuristiques maison complètent checkov, ne le remplacent pas.
Des règles sécu qui attrapent ce que checkov rate expertise
Le constat
Un scan checkov « propre » n'est pas forcément sûr. En vrai, l'agent a laissé passer un s3:ListAllMyBuckets sur arn:aws:s3:::* — checkov-clean, mais un écart au least-privilege qu'un reviewer senior noterait.
Les règles maison
tfforge ajoute des règles provider-aware plus fines : wildcard de service (s3:*, pas juste *), accès S3 account-wide, iam:PassRole sur * (escalade de privilèges), SSH/RDP ouvert à 0.0.0.0/0, base publicly_accessible = true, HTTP en clair en transit — chacune avec une sévérité.
Multi-cloud AWS · GCP · Azure
L'agent, la garde et checkov marchent avec n'importe quel provider (AWS, GCP, Azure, cloud privé VMware/OpenStack…). Et l'analyse maison couvre les 3 hyperscalers : GCS bucket public, firewall ouvert, rôles IAM primitifs (GCP) ; NSG ouvert, blob public, TLS 1.0 (Azure) — chaque règle ne se déclenche que sur SON provider (un fichier AWS ne trigger pas de règle GCP). Le reste passe par checkov + l'agent + la garde.
Pas que la sécu : 3 catégories
Le scan classe en security, version et best-practice. La catégorie version attrape les syntaxes dépréciées (inline S3 acl/versioning sur le provider moderne), un provider AWS périmé (v3 ou moins), un required_version absent — l'agent modernise le code vis-à-vis des maj TF, pas seulement le sécurise. best-practice : région hard-codée, required_providers absent, pas de backend distant.
Pourquoi ça compte
C'est ce qui montre ton expertise DevOps — pas juste « j'appelle checkov ». Tu sais ce qui compte vraiment (un port SSH ouvert au monde = comment les gens se font vraiment breach) ET ce qui vieillit mal (une syntaxe TF dépréciée). Tout est déterministe : zéro token.
Testé adversarialement fiabilité
Le vrai gage de qualité : le scanner est durci par des tests adversariaux. Des agents génèrent des cas piégeux (IPv6 ::/0, bucket public par policy et pas ACL, secret dans un heredoc user_data, Aurora non chiffré…), on mesure les faux négatifs/positifs et on corrige. Résultat verrouillé par tests : il attrape ce qui doit l'être et reste silencieux sur du bon code (un s3:* dans un Deny ne déclenche rien). Un scanner qui crie à tort est pire qu'inutile — celui-ci ne le fait pas.
tfforge scan <dir> — le mode CI, SANS IA intégration
C'est quoi
Une sous-commande déterministe, sans LLM, sans clé API, sans tokens : tfforge scan ./infra --json --fail-on high. Elle lance l'analyse de sécurité et sort en code non-zéro quand des findings atteignent le seuil.
Quand
Dans un pipeline CI : le même cerveau sécu que l'agent, mais appelable en une ligne pour gater une PR. --json pour un rapport machine, --fail-on none pour du report-only.
Pourquoi ça compte
Ça montre que tu penses INTÉGRATION, pas juste démo interactive. Un agent, c'est bien ; un agent dont la partie déterministe gate un CI, c'est un produit.
À dire en entretien : « Mon agent a un mode CI sans IA : tfforge scan --json --fail-on high, exit code non-zéro sur findings. La même logique de sécurité, exécutable dans un pipeline pour bloquer une PR non conforme. »
terraform_validate — le gate syntaxe
C'est quoi
Valide que la config Terraform parse et est cohérente, avant de scanner ou planifier. Inutile de scanner du code qui ne compile pas.
Pourquoi
C'est la première étape de la boucle : si validate échoue, l'agent corrige et re-valide avant d'aller plus loin.

La garde policy-as-code (le différenciateur)

le moat

Ce qui distingue tfforge d'un « agent qui lance terraform ». Le même concept que les guards d'opsforge, appliqué aux actions de l'agent — ton portfolio raconte une seule histoire cohérente.

terraform_apply / terraform_destroy, sous garde
C'est quoi
Une politique déclarative (règles action × contexte → allow/warn/confirm/deny, first-match-wins) que chaque action mutante/destructrice traverse avant de s'exécuter. La politique par défaut : DENY destroy sur prod, CONFIRM apply sur prod.
Fail-closed (le point critique)
La garde échoue en mode fermé : un destroy sur un contexte qu'elle ne peut pas prouver non-prod est bloqué. Elle lit le workspace Terraform passivement (fichier .terraform/environment), pas juste le nom du chemin — donc une prod qui ne s'appelle pas littéralement « prod » est quand même protégée.
Read-only libre, YAML custom
Les actions en lecture seule (plan, scan, validate) contournent la garde. Les politiques YAML personnalisées sont supportées — la logique de sécurité est de la donnée versionnable, pas codée en dur dans l'agent.
À dire en entretien : « La même policy-as-code qui me garde au clavier (opsforge) garde mon agent IA (tfforge). Mon agent ne peut pas détruire la prod — et je l'ai prouvé par des tests, y compris le cas où la prod ne s'appelle pas “prod” : la garde échoue en mode fermé plutôt que de deviner. Et je reste honnête : c'est un filet solide, pas une barrière absolue — je le combine avec des credentials cloud à privilèges minimaux (défense en profondeur). »

Gros repos & LLMOps

2 briques

Ce qui fait passer l'agent de démo à outil qu'on laisse près de la vraie infra : lisibilité sur un gros repo, et la couche audit + coûts que les équipes exigent.

terraform_plan — un plan lisible pour un gros repo
Le problème
Sur un gros repo, la sortie brute de terraform plan fait des centaines de lignes — illisible pour un humain, et coûteux (voire hallucinogène) à faire avaler à un LLM.
La solution
tfforge parse le plan en JSON structuré (terraform show -json) et produit un tableau : compteurs +create / ~update / -destroy / ±replace, changements destructeurs en premier (rouge), un warning ⚠, plafonné à 40 lignes + un rollup par type pour le reste.
L'insight qui scale
L'agent ne reçoit qu'un digest compact (pas les 500 lignes) → un gros plan n'explose ni le contexte ni la facture de tokens. Le déterministe compte, l'IA explique — le même pattern que KubeForge.
À dire en entretien : « Pour scaler sur un gros repo, je ne balance pas le plan brut au LLM — je le parse en Go de façon déterministe et je ne lui donne qu'un résumé. Le déterministe compte, l'IA explique. C'est la bonne architecture LLMOps : fiable, prévisible, économe en tokens. »
Audit + coûts LLMOps
C'est quoi
Chaque tour du modèle et chaque action gardée sont écrits dans un journal d'audit JSONL (~/.local/state/tfforge/audit.jsonl) — une trace revue de ce que l'agent a fait et de ce que la garde a bloqué, pas seulement ce qui s'est exécuté.
Les coûts & le budget
La consommation de tokens est valorisée en coût USD estimé, affiché dans un résumé de run (N turns · … tokens · M tool call(s) (K denied) · ~$cost). Un budget (TFFORGE_MAX_COST) arrête le run avant qu'il ne dépasse un plafond — du FinOps pour agents.
Optimisé pour consommer peu
L'agent est tuné pour économiser les tokens : il édite chirurgicalement (edit_file) au lieu de réécrire un fichier entier, ne planifie qu'une fois, reste concis. Toute l'analyse sécu/version/best-practice est déterministe (0 token). Et TFFORGE_MODEL=claude-haiku-4-5 le fait tourner ~3× moins cher. « Tout doit être optimisé. »
Pourquoi ça compte
Un agent autonome près de la vraie infra doit être reviewable (« qu'a-t-il fait, qu'a-t-il tenté, qu'a bloqué la garde ? ») et son coût visible. C'est exactement ce que les équipes demandent pour mettre un agent en production — et c'est là que ton profil DevOps devient rare (AI Platform / LLMOps Engineer).
À dire en entretien : « J'ai ajouté la couche prod qui manque à la plupart des démos d'agents : un audit log structuré de chaque action et décision de garde, et le coût par run. Le journal est du JSON ligne-par-ligne à un chemin connu → un tail Vector/Fluent Bit l'expédie vers Loki ou un SIEM. C'est ce qui rend un agent gouvernable. »
